## Q11. Denoiser: FullSubNet vs. an installable alternative

**Question.** The paper's denoiser is FullSubNet (Audio-WestlakeU). Is it
installable as a normal Python dependency for this repo?

**Finding.** FullSubNet has **no PyPI package**. It is distributed only as a
GitHub repo (`Audio-WestlakeU/FullSubNet`); checkpoints live on GitHub
Releases, not a package registry; the README/Wiki instruct `git clone` +
`pip install -r requirements.txt` + manual checkpoint download, not
`pip install fullsubnet`.
[GitHub - Audio-WestlakeU/FullSubNet](https://github.com/Audio-WestlakeU/FullSubNet)

**Alternative found.** DeepFilterNet3 (`Rikorose/DeepFilterNet`) is on PyPI as
`deepfilternet` (0.5.6), installs with `pip install torch torchaudio` +
`pip install deepfilternet`, ships pretrained weights inside the package (no
separate manual checkpoint step), and operates on full-band 48 kHz audio by
design — the same full-band motivation FullSubNet cites (Hao 2021 fuses
full-band + sub-band; DeepFilterNet's own framing is "Low Complexity Speech
Enhancement Framework for Full-Band Audio (48kHz) using Deep Filtering").
[deepfilternet · PyPI](https://pypi.org/project/deepfilternet/)

**Decision (locked this session, D2).** Default denoiser = `deepfilternet`.
`ffmpeg afftdn` (already available, zero new dependency) is the fallback
behind the same `Denoiser` protocol. FullSubNet stays a **deferred, named**
option — vendoring it later is a config addition, not an interface change.

**Consequence for the spec.** DeepFilterNet3 requires **48 kHz** input/output;
the stage must resample 16 kHz → 48 kHz → denoise → 48 kHz → 16 kHz. This
resample round-trip is new relative to the paper's description and must be
named explicitly (§10 pipeline design).

## Q12. Loudness normalization: single-pass vs. two-pass `loudnorm`

**Question.** The paper cites FFmpeg's EBU R128 `loudnorm` filter. Spec
v1/v2's shared success criterion #11 requires byte-identical output on repeat
runs. Does `loudnorm` meet that as specified?

**Finding.** FFmpeg's `loudnorm` has two modes. **Dynamic (single-pass,
default)** applies real-time adaptive gain — the filter's own dynamic
behavior is history-dependent frame-to-frame, which is fine for streaming but
not what "two runs on the same input produce byte-identical output" implies
when the *same* frame's gain can differ depending on filter internal state
warm-up. **Linear (two-pass)** first measures the file with
`print_format=json` (emits `input_i`, `input_tp`, `input_lra`,
`input_thresh`), then re-runs with those `measured_*` values plus
`linear=true`, applying one fixed, calculable gain across the whole file.
[Two-pass loudness normalization with FFmpeg loudnorm (the right way) — dev.to](https://dev.to/masonwritescode/two-pass-loudness-normalization-with-ffmpeg-loudnorm-the-right-way-1nm3)
[loudnorm — FFmpeg filter docs](https://ayosec.github.io/ffmpeg-filters-docs/8.0/Filters/Audio/loudnorm.html)

**Caveat found.** In linear mode, loudnorm cannot always simultaneously hit
integrated loudness (I), loudness range (LRA), and true-peak (TP) targets —
a single fixed gain may satisfy I while missing LRA/TP exactly. This is
expected and does not block determinism: the *same* input + config always
produces the *same* gain and thus the *same* output.

**Decision.** v2 requires the **two-pass, `linear=true`** invocation as the
only supported mode; single-pass dynamic `loudnorm` is out of scope. Measured
values (`I`, `LRA`, `TP`, `thresh`) are recorded in `provenance.json` as
non-sensitive acoustic scalars.

## Q13. Channel normalization tool: SoX GSM Full Rate support

**Question.** Does SoX actually support the paper's GSM Full Rate / 13 kbps
encode-decode round trip and the `compand` + bandpass steps, and is SoX
present on the target machine?

**Finding.** SoX has built-in GSM 06.10 (GSM "Full Rate", 13 kbit/s) encode
and decode support, **contingent on being built against libgsm** — checkable
via `sox -h` under supported file formats. SoX's own docs note the round trip
is lossy by design (same as any telephony codec: A-law, GSM), which matches
the paper's framing of GSM as "a lower bound of acceptable audio quality."
Dynamic-range compression is `compand` (single-band) or `mcompand`
(multi-band with per-band crossover frequencies); band-limiting is the
`bandpass` two-pole Butterworth filter with a center frequency and
3 dB-point width — directly usable for the paper's 200–3400 Hz band.
[man SoX (1)](https://manpages.org/sox)
[SoX GSM support / Full Rate — Wikipedia cross-reference](https://en.wikipedia.org/wiki/Full_Rate)

**Machine check (this repo, 2026-09-20).** `command -v sox` → not found.
`ffmpeg` 6.1.1 *is* installed and links `libgsm`, and has `highpass`/`lowpass`/
`acompressor`, so the paper's steps 1–2 are technically coverable by ffmpeg
alone. The user chose SoX + ffmpeg (paper-faithful) over ffmpeg-only for this
spec (decision D3, this session) — **SoX must be documented and probed as an
external prerequisite**, not assumed present.

**Decision.** `channel_norm` stage shells out to `sox`. `say-transcribe
diagnose` reports `sox`: `found` / `not found`, and separately whether `sox -h`
lists `gsm` under supported formats (some distro builds omit optional GSM
support). No pure-Python SoX reimplementation.

## Q14. VAD: Silero VAD scope vs. existing pause-timing features

**Question.** `speech_features.features.acoustic.timing` already computes
pause/voiced-segment statistics from an internal energy-based VAD
(`_energy_vad` in `acoustic.py`). Does adding Silero VAD duplicate that, or
does it serve a different purpose?

**Finding.** Silero VAD (`snakers4/silero-vad`, MIT) installs via
`pip install silero-vad`; its published API
(`load_silero_vad` / `read_audio` / `get_speech_timestamps`) supports 8 kHz
and 16 kHz mono float32 input and returns speech-interval timestamps, not
per-token or per-utterance features.
[GitHub - snakers4/silero-vad](https://github.com/snakers4/silero-vad)
[silero-vad · PyPI](https://pypi.org/project/silero-vad)

`speech_features`'s existing pause/voiced-segment features
(`time_pause_count`, `time_voiced_segment_mean_s`, etc., in
`src/speech_features/features/acoustic/timing.py`) are computed **at
extraction time**, from the **original** audio, restricted to aligned
utterance intervals via `_merged_intervals`. Those already satisfy the
paper's stated VAD deliverable ("average duration of voiced segments and the
number of pauses"). If `say_transcribe`'s VAD stage also emitted competing
pause statistics into the draft document, `say-features` would either ignore
them (dead output) or a future contributor could wire them in and silently
create two disagreeing pause-count implementations reading two different
audio branches (original vs. preprocessed).

**Decision.** Silero VAD's role in `say_transcribe` v2 is **ASR chunking and
diarization-turn hinting only** — it runs on the preprocessed branch and
narrows what the ASR/diarization stages process; it does not write pause or
voiced-segment features into the SAY document. `speech_features` remains the
single source of truth for pause/voiced-segment metrics, computed from the
**original** audio (branch decision D1). This is recorded as an explicit
non-goal in the v2 spec rather than left implicit.
