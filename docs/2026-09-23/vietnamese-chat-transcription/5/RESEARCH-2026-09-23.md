## 2. transcribe flow (batchalign)

CLI entry `python/batchalign/cli/transcribe.py`:

1. `_build_asr` builds the ASR backend for the requested `AsrEngine` (`transcribe.py:255`).
2. Utterance segmentation is a separate backend, built by `_build_utseg` (`transcribe.py:329-361`),
   *unless* the ASR engine segments itself (`_engine_self_segments`, `transcribe.py:86`). Its
   docstring: *"Build the CHATUtterance segmenter for `lang`, or None if BA2 ships no utterance
   model for it (then ASR segments stand as utterances)."*
3. `_UTSEG_LANG_3` (`transcribe.py:321-326`) is the only language map consulted:
   ```
   {"eng": "eng", "cmn": "zho", "zho": "zho", "yue": "yue"}
   ```
   Malayalam is handled separately (`ba.MalayalamSaTBackend()`, `transcribe.py:337`). Any other
   `alpha_3`, including `vie`, misses the dict and hits the `None` branch, logging *"no TalkBank
   utterance-segmentation model for %r; retaining ASR-provided utterance boundaries"*
   (`transcribe.py:345-349`).
4. `python/batchalign/backends/utseg/chatutterance.py:29-35` (`_UTTERANCE_RESOLVE`) confirms the same
   gap independently: only `eng` → `talkbank/CHATUtterance-en` and `yue` →
   `PolyU-AngelChanLab/Cantonese-Utterance-Segmentation` are registered.
5. `--diarize` runs a dedicated speaker backend *after* utterance segmentation so its labels are
   final (`transcribe.py:190-199`).
6. `ba.recipes.transcribe(...)` assembles ASR + speaker + utseg backends into one pipeline
   (`transcribe.py:225-232`).

**Vietnamese has no dedicated utterance model in batchalign.** ASR segment boundaries are the
fallback batchalign itself uses for every language outside `{eng, cmn, zho, yue, mal}` — this is
the basis for Decision D4 (utterances = ASR segments), not a shortcut we invented.

## 3. morphotag flow (batchalign)

`python/batchalign/backends/morphosyntax/stanza.py`:

- `_preprocess_text` (`stanza.py:718-736`) runs CHAT-marker cleanup before Stanza sees the line:
  `render.clean_sentence(text)`, then `_CLEANUP_RE.sub("", line_cut)`. `_CLEANUP_RE`
  (`stanza.py:234`) is:
  ```python
  re.compile(r"\+<|\+/|\(|\)|\+\^|\+//|\+\.\.\.|_|[#]")
  ```
  **This strips every literal underscore from the input line.** It exists to remove CHAT notation
  markers, not word-joiners — but it means batchalign's own preprocessing cannot be run unmodified
  over `_`-joined Vietnamese multi-syllable words (Decision D2): the joiner would be silently
  deleted before Stanza ever tokenizes.
- MWT is requested per language via an exclusion list, not an inclusion list:
  `_MWT_EXCLUSION` (`stanza.py:201-224`) = `{hr, zh, zh-hans, zh-hant, ja, ko, sl, sr, bg, ru, et,
  hu, eu, el, he, hi, af, ga, da, ro}`. `vi` is **not** in this set, so
  `config["processors"]["mwt"] = "default"` is set for it (`stanza.py:345-346`) — batchalign would
  request Stanza's MWT expander for Vietnamese if run directly, even though UD-VTB (§5) is a
  single-token-per-syllable treebank with no MWT training data.
- `python/batchalign/backends/morphosyntax/ud/tokenize.py:56-90` (`tokenizer_processor`, ported
  from BA2 `ud.py`) re-aligns Stanza's internal tokenization to `sent.split(" ")` — the space-split
  passage is the authoritative CHAT word boundary, and Stanza's own segmentation is forced to match
  it via a char-level DP aligner (`dp.py`, not re-inspected this pass). This part is
  language-generic: it does not special-case Vietnamese, and it is *why* D2's `_`-joined words work
  as single CHAT tokens as long as they survive to this stage as one space-delimited unit (i.e.,
  without going through `_CLEANUP_RE` first).
- `python/batchalign/backends/morphosyntax/ud/render.py`:
  - `handler(word, lang)` (`render.py:873-...`) builds the `%mor` lemma text and itself strips
    underscores: `target = target.replace("_", "")` (`render.py:921`), right before
    `target.replace("+", "")` (`render.py:922`). A second, unrelated use of a leading `_` appears at
    `render.py:1290`, where a token text starting with `_` marks a CHAT clitic/auxiliary during
    `%gra` head assignment (ported from BA2 `ud.py:369-411`) — this is CHAT's own notation for
    clitics, a different meaning of `_` from our word-joiner, and another reason not to run
    `_`-joined Vietnamese text through batchalign's renderer unmodified.
  - `,` is rendered as `cm|cm` in three places (`render.py:938`, `:1140`, `:1165`), confirming the
    SPEC's punctuation rule.
  - Root-head invariant: a word is `%gra` root iff `head == 0 and deprel.lower() == "root"`
    (`render.py:283-284`, `:674`, `:770`), enforced as a joint invariant with an anomaly raised on
    mismatch (`render.py:283-284`).
  - `parse_sentence` (`render.py:1225`) is the entry point that walks Stanza's per-sentence output
    into the `%mor`/`%gra` tier structures.

## 5. Language-support resolution (corrects a prior-window claim)

A prior pass claimed "`vie` is in `SUPPORTED_STANZA_CODES`." That constant does not exist in the
Python tree; it is generated on the **Rust** side. What we verified directly:

- `python/batchalign/backends/morphosyntax/ud/lang.py:13-34` (`to_stanza`) is a generic
  ISO-639-3 → Stanza alpha-2 converter via `pycountry`, with one hardcoded special case (`yue` →
  `zh-hant`). It has **no allow-list** — `vie` converts to `vi` through the generic `pycountry`
  path like any other three-letter code.
- `python/batchalign/backends/morphosyntax/stanza.py:397` calls `stanza.Pipeline(lang=lang, ...)`
  directly with whatever code reaches it — no Python-side language gate.
- `scripts/generate_stanza_language_table.py:1-9` generates `STANZA_SUPPORTED_ISO3` /
  `SUPPORTED_STANZA_CODES` for the **Rust** crates (`request.rs`, `stanza_languages.rs`) from
  Stanza's own `resources.json` via `build_stanza_capability_table()` — i.e. that table mirrors
  Stanza's actual package coverage, not batchalign's curated docs.
- `book/src/batchalign/reference/languages/overview.md` lists 9 languages (Dutch, Portuguese,
  French, Italian, Hebrew, Japanese, Cantonese, Mandarin, Malayalam) with authored UD-defect
  mitigations. This is a **curated/tested subset**, not the Rust-side capability table — its
  absence of Vietnamese means no one has written Vietnamese-specific UD-VTB mitigation docs, not
  that Stanza/batchalign reject the `vi` code.

**Conclusion:** Vietnamese is Stanza-capable at the Python layer (generic pipeline construction, no
gate), consistent with Stanza officially shipping a `vi` (UD-VTB) package, but it is outside
batchalign's documented, defect-mitigated language set. UNVERIFIED at the byte level: the actual
generated Rust `SUPPORTED_STANZA_CODES` list and `resources.json` contents were not fetched this
pass — if the CLI-level Rust gate is ever a dependency (it is not, since D3 builds our own
pipeline), that file should be pulled before relying on it.
