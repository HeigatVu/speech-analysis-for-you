- `phowhisper-large` previously returned `MODEL_UNAVAILABLE` on both cells, and the cause was measured rather than guessed: it is a CUDA out-of-memory inside word-timestamp decoding. `asr.py` reports load failure and inference failure under the same redacted code, so the code alone cannot distinguish the two, and the cause is deliberately swallowed `from None`. Two separate costs were isolated. First, the post-hoc `model.half()` copied the 6.2GB fp32 checkpoint onto the card before converting, leaving 6.64GB reserved after load, against 3.34GB when fp16 is requested at load time. Second, word timestamps cost about 4.4GB more per window than segment ones: the same dense 18.8 s p001 window peaks at 9.06GB with `return_timestamps="word"`, 4.63GB with segment and 4.64GB with no timestamps, and the word figure is flat across `max_new_tokens` 400, 200 and 90 and across the temperature-fallback tuple, so neither the token cap nor the fallback is the driver.
- The per-window ceiling is real and is not fragmentation. Window 0 of p001 fits at 8.90GB peak; window 1 needs 11.34GB of live PyTorch allocation and OOMs with 7.81 MiB free on a card whose usable capacity is 11.49 GiB (12 335 316 992 bytes) — in both the default allocator and with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, so the 645 MB of reserved-but-unallocated memory is not the difference. Shrinking the token cap is not a usable lever either: cap 90 fits at 9.36GB but caps 180 and 363 both OOM, and a cap small enough to fit would silently truncate dense speech. The card, not the window and not the decode length, is the limit.
- Two changes make the GPU run fit, with no change to window boundaries or token caps. `PhoWhisperBackend.load` now asks for fp16 at construction on CUDA (`dtype=torch.float16`) instead of loading fp32 and calling `.half()` afterwards; the weights that end up on the card are the same fp16 weights, so no decode result changes, and 3.3GB of transient reservation disappears. `PhoWhisperBackend` also gained `timestamps: str = "word"`, validated against `("word", "segment")`, plumbed through `make_asr_backend(..., timestamps=...)`, and the benchmark's `_default_asr_factory` asks for `"segment"`.
- Requesting segment timestamps for the benchmark is legitimate because the benchmark scores text only — `score_uncapped` over `items_from_texts([segment.text for segment in result.segments])` — and word and segment timestamps decode byte-identical text. Verified on p001 window 0: 144 characters both ways, `word == segment` true, while `return_timestamps=False` differs (152 characters) because only the timestamp modes install `WhisperTimeStampLogitsProcessor`.
